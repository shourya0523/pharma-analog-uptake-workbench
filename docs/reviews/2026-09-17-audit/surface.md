**Simpler alternative**: none obvious that preserves the value — the problem (one figure per quarter, per series) genuinely needs a stable identity key and a stored decision; a purely computed-on-read approach would just move the same logic into every reader (which is exactly what it replaces). This is a case where the complexity is earned. **Leave as is.**

### `main.py::_resettle_series` (`main.py:541-555`) vs `api/products.py::resolve_unresolved_quarter` (`api/products.py:713-745`) — the "same question from four places" is answered two different ways
**Wrong/fragile, verified.** The commit message for `dde7fb0` says explicitly: "the three review write paths... each left it stale in a different way," and frames the fix as "the same question asked from four places and the answer has to be the same each time." But the two implementations differ:
- `main.py:541-555 _resettle_series` (used by `patch_datapoint` and `validation_action`) re-stamps `series_identity` on **every** datapoint of the job before calling `select_job_series` (`stamp_series_identity(job, row)` in a loop over all rows, then `select_job_series(db, job, rows)`).
- `api/products.py:713-745 resolve_unresolved_quarter` stamps `series_identity` **only on the newly created datapoint** (`stamp_series_identity(job, datapoint)` at line 717), then calls `select_job_series` over `db.query(DatapointORM).filter_by(job_id=job.id).all()` — the pre-existing rows keep whatever `series_identity` they already had.
`select_job_series` groups by `SeriesReading(identity=row.series_identity or "", ...)` (`orchestrator.py:559`), so any row with a `None` identity collapses into the identity bucket `""` for its quarter. That only matters for a database that has un-stamped legacy rows (an old DB migrated in), but it's exactly the class of edge case this series of commits is otherwise careful about (`series_identity.py`'s own docstring: "written when the row is, and again once the labels are final"). `resolve_unresolved_quarter`'s path does not re-heal legacy rows the way the other two paths do.
**Do**: have `resolve_unresolved_quarter` call the same `_resettle_series` helper (move it out of `main.py` into a shared module, e.g. `pipeline/orchestrator.py` beside `select_job_series`) instead of the narrower inline stamp-one-row-then-select. Preserves the value, removes one of the two implementations, and closes the legacy-row edge case. Low risk — it's strictly more re-stamping of already-correct data in the common case.
I verified this by reading the two code blocks (`main.py:541-555`, `api/products.py:713-745`) side by side; I did not construct a DB with an un-stamped legacy row to reproduce the divergent output — that part is inferred from the code, not run.

## Surface: the dashboard chart's own selection logic never reads the field built to answer it

**Verified, and this is the most consequential finding in the surface scope.** `frontend/src/pages/dashboardModel.ts:141-181 selectOneFigurePerPeriod` (plus `rankOf`, `reconciliationChoseIt` at lines 97-113) re-implements "which reading is the one for this quarter" using `scope_rank`, raw value-equality, and a fallback to `point.citation.corroborated_by` — a marker set by the pipeline's older, coarser `_reconcile_with_llm` stage (`orchestrator.py:3009-3016`, grouped on `(period, scope_key, formulation)`, not on `series_identity`). It does this **despite the backend now shipping the authoritative answer on every point**: `dashboard/series.py:360-361` puts `series_identity` and `series_selection` on every row of the `series` payload, and `frontend/src/api/client.ts:99-100` types both fields. Confirmed by exhaustive grep — `series_identity`/`series_selection` appear nowhere in `dashboardModel.ts`:
```
grep -rn "series_identity\|series_selection\|corroborated_by" frontend/src/
frontend/src/api/client.ts:99-100        (typed only)
frontend/src/pages/ProductDetailPage.tsx:252-254   (rendered — correct usage)
frontend/src/pages/DashboardPage.tsx:359-361       (series_identity rendered in drill panel; series_selection is not)
frontend/src/pages/dashboardModel.ts:106,111       (corroborated_by — the OLD mechanism)
```
Why this matters in practice, not just in principle: `select_job_series`'s "cell" is `(row.period, row.period_type)` **without** the identity (`orchestrator.py:558`), so two different `series_identity`s that both win their own group (e.g. a product's own line and a "Product + Partner" combined line, or Worldwide vs. a differently-labelled Worldwide reading) can both legitimately carry `series_selection == "selected"` for the same quarter, at the same `scope_rank`. The default payload (`include_held=False`) ships both. `selectOneFigurePerPeriod` then has to arbitrate between two backend-endorsed selected readings, and the only tool it has for that is the stale `corroborated_by` signal — which was computed by a stage that groups more coarsely and runs *before* labels like `reported_as` are finalized in some paths (per `stamp_series_identity`'s own docstring, identity is "written again once the labels are final" because reconciliation changes them). `dashboardChartSelection.test.ts:106-129` tests this exact ambiguity ("draws the reading reconciliation chose when two at one scope disagree" / "marks a period contested") using synthetic points that never set `series_identity` at all — i.e. the test suite for this exact scenario was never updated to reflect that the backend now has an opinion.
**Do**: in `selectOneFigurePerPeriod`, prefer `series_selection === 'selected'` combined with `series_identity` grouping before falling back to `corroborated_by`/value-equality — and when two different `series_identity`s both survive, say so explicitly (e.g. surface `reported_as` in the tooltip) rather than silently picking one via a stale signal. This removes the parallel selection logic for the common case and keeps a narrow, honest fallback only for identity-less legacy payloads.
**Risk**: medium — touches the one piece of frontend logic with the most history of visible bugs (item 1a in the 006 register was exactly "the chart plots the wrong number"); needs the 8 existing tests in `dashboardChartSelection.test.ts` re-derived against real `series_identity`/`series_selection` fixtures, not just patched.

### The "third shape" the brief asked about — verified, and this is the substantive wiring gap
The new `series_identity`/`series_selection`/`normalize_geography` machinery does **not** reach `peak_sales.py` or fully reach `uptake.py`:
- `uptake.py:83-103 _matches_peak_scope` was patched in `21d20a0` to call `normalize_geography` from `pipeline/series_identity.py` (`uptake.py:24,100`) — a real, narrow fix for the geography-spelling problem (item 2b).
- `peak_sales.py:116-131 scope_key` — the function `one_observation_per_period`, `aggregate_comparable_sales`, and `_partitions` all key off of — was **not** touched by the same commit and still compares raw `row.geography` with no normalization:
```
grep -n "normalize_geography\|scope_key\|geography_normalized" backend/app/analytics/*.py
peak_sales.py:116  def scope_key(...) -> tuple[str, str, str, str, str | None]:   # uses row.geography raw
peak_sales.py:154,184,199,215,277   scope_key(row) called — never normalized
uptake.py:24        from app.pipeline.series_identity import normalize_geography
uptake.py:100       normalize_geography(row.geography) == normalize_geography(peak.geography)
```
So the same defect this branch explicitly fixed in one file (`uptake.py`) is still present in its sibling (`peak_sales.py`) — a product reporting a U.S. line as "U.S." one year and "US" the next would still fail to form a 3-year comparable partition in `_partitions` (`peak_sales.py:267-283`), which is exactly the shape of bug `21d20a0` fixed elsewhere. This is a genuine, verified gap, not a style nit: `_mature_observed_peak` requires 3 consecutive years in one partition (`peak_sales.py:244-245`), and a geography-spelling split would silently produce two 1-2-year partitions instead, each refusing for `insufficient_annual_history` — a wrong refusal that reads as "not enough data" when the data was there under two spellings.
- Beyond geography, there is no shared "is this the same series" primitive at all: `series_identity()` (`pipeline/series_identity.py:143-183`) is an 8-part string (issuer, product, scope, geography, formulation, **reported_as**, currency, period_type); `peak_sales.py::scope_key` is an independent 5-tuple (currency, geography, revenue_scope, period_basis, **formulation_scope** — a field name that doesn't exist anywhere in `db/models.py`, confirmed empty grep) with **no `reported_as` or issuer/product field at all**. `uptake.py::_matches_peak_scope` is a third, separate 5-field comparison that doesn't call `scope_key` either.
- **What the wiring will need that the code does not yet give**: (a) `SalesObservation`/`AnnualSales`/`PeakEstimate` (`peak_sales.py:56-93`) have no `reported_as` or `combined_line` field, so a naive wiring that constructs `SalesObservation` from `DatapointORM` rows would re-admit exactly the Pombiliti+Opfolda combined-line-counted-as-the-product's-own-revenue bug (item 1c/2c in the 006 register) *inside* layer 3, even though `series_identity`/`reported_as` already exist on the datapoint and already solve this for layer 1's own export/dashboard. (b) `peak_sales.py::scope_key` needs the same geography normalization `uptake.py` got. (c) `analog_matching.py::ProductProfile` (`analog_matching.py:38-44`, confirmed via grep) still has no revenue-basis/scope field — `569b89e` added `indication_area` (disease) but item 2c's actual finding (a worldwide analog scored against a U.S.-only target with nothing checking the mismatch) is still open.
- **Do**: before wiring any of the four `NOT_WIRED` entry points, either (i) give `SalesObservation` a `series_identity` field and construct it directly from the already-computed value, retiring `scope_key` as a second implementation, or (ii) at minimum add `reported_as`/`combined_line` to the dataclasses and make `scope_key` call `normalize_geography`. This is a "don't wire it yet as-is" finding, not a simplification of code that ships today — cost is zero now (nothing calls it), but it is exactly the kind of two-modules-grow-the-same-abstraction-twice risk the audit was set up to catch, and it will become a live defect the moment any of these functions gets a caller.
